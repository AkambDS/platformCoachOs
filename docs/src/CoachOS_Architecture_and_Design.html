1Product and roles

Coaches today juggle notes in Notion or Docs, Calendly plus Google Calendar, Stripe plus QuickBooks, and a pipeline spreadsheet. CoachOS replaces that set with one system per workspace, which is the tenant boundary. A user belongs to exactly one workspace. Their role sets a baseline, and the owner can widen or narrow it per section.

RoleScopeHow it's enforced
business_ownerEverything in the workspace: billing, team, integrations, Email CommunicationRole checks on viewsets; owner-only routes via RoleRoute
coachOwn clients and schedule; more sections if grantedTabPermission view / edit / delete per section
assistant · limitedOperational, then further-restricted accessSame per-tab overrides
platform_adminCrosses workspaces: CoachOS's own consoleIsPlatformAdmin on /api/superadmin/*
portal_clientThe coach's client, in the self-serve portal onlySeparate JWT scope (see §4)

The frontend mirrors these rules: TabRoute and RoleRoute wrap every gated page, so a role that would get a 403 never sees the UI in the first place.

3Request path and tenant isolation

All workspaces share one database. A request becomes tenant-scoped by passing the chain below. Each workspace-owned model inherits WorkspaceModel and carries a workspace foreign key.

Design risk: only one isolation layer. The RLS policies (tenant_isolation, plus portal_isolation on goals) look like a second line of defence, but they don't run: in production the application connects as coachos_admin, which owns the tables, and the tables don't use FORCE ROW LEVEL SECURITY, so Postgres exempts the owner. Only 12 of 34 workspace tables have policies at all. A single viewset that forgets its workspace filter would leak across tenants. Fix (planned in PHASE2.md, P2-2/P2-3): a non-owner runtime role, FORCE + WITH CHECK on every workspace table, and an explicit tenant context for Celery tasks and webhooks, which run without the request middleware.

Writes are scoped too (since 2026-10-08). Reads were always filtered by workspace, but writable foreign keys (client, coach, deal, …) used DRF's default lookup over every workspace's rows, so workspace B could create an invoice, deal or session against workspace A's client. Every serializer with a writable FK now mixes in WorkspaceScopedSerializerMixin (apps/accounts/tenancy.py): the FK resolves only within the caller's workspace and, for non-owners, only to rows they can already read (a coach can pick only their own clients). It fails closed with no request in context. Login also refuses a non-admin user with no workspace instead of attaching them to the oldest one. backend/test_tenant_isolation.py covers cross-workspace and coach-vs-coach reads and writes, portal client-vs-client, and includes a guard test that fails if a future serializer adds an unscoped writable FK.

The DemoWorkspaceReadOnlyMiddleware sits right after the tenant middleware. It is real Django middleware, not a DRF default permission, because most viewsets declare their own permission_classes, which would silently replace a global default. Login, logout, refresh, demo-lead capture and the portal demo-login are exempt.

6Data model

Supporting tables: GoogleCalendarWatch (per-coach push channel), PortalLoginCode, EmailLog, AccessLog and AuditLog, ErrorLog, FeedbackTicket, and platform-level DemoLead, MaintenanceBanner and PlatformInvoice/Payment.

7Scheduling and calendar

A session is an Activity with a coach, a client and one of 8 built-in, renameable types (appointment, session, call, task, training, travel, client communication, custom). Recurring series are written out as real rows linked by recurrence_id, up to repeat_until or one year ahead.

Self-serve rescheduling

The emailed reschedule link offers a slot picker built from that client's CoachAvailabilityRules. It checks busy time against the coach's confirmed sessions and every other client's pending proposal, so two clients can't claim the same slot. Without availability rules, the link falls back to a free-text request. The portal's reschedule request is always free text.

Zoom. From Calendar or a client record, the coach clicks to create a meeting. The call happens in the request and stores join_url on the session. The integration subscribes to no Zoom webhooks and keeps no other Zoom data.

8Billing and payments

CoachOS's own billing of its workspaces is a separate system. dj-stripe is installed, but PlatformInvoice billing is done by hand from the superadmin console.

9Sales pipeline

Deals move through workspace-configurable stages: Lead – New → Discovery Scheduled → Discovery Completed → Proposal Sent → Verbal Yes → Active Client, plus On Hold and Closed – Lost. Every move writes StageHistory. Creating a deal from the New Client form is opt-in.

Out of scope by design: assessments, messaging and contracts (contracts use their own signed link). Branding shows the workspace's logo and name.

Sign-in screens. Both logins share one layout: an editorial left column, a gold-topped card on the right, and an ombré background (warm paper to soft blue, .auth-ombre). A decorative canvas animation sits behind them, laid out from the real page elements (marked data-flow-*) so it never crosses text or the form, and the card title carries a gold North Star (FlowStar) that pulses as chains of dots arrive. The coach login (NorthStarFlow) fans lines in from the bottom-left corner to each feature bullet, then on to the card. The client portal (GoldenThreadFlow, modelled on LangSmith's sign-in page) fans curves in from the left edge into a straight gold line along the rule under the intro text, which rises into the card. Both hide on the stacked mobile layout and render one still frame under prefers-reduced-motion.

12Library, documents and contracts

Contracts and client messages. A ClientMessageDraft is emailed with optional attachments from S3. If it needs a signature, the client signs at a public /contract/sign/<token>/ link. The draft then becomes signed and the coach receives a contract_signed notice.

13 AI session-note drafts

On a structured session note, Suggest with AI sends the coach's raw notes to Anthropic through POST /api/clients/{id}/notes/suggest/ and returns a drafted Coach Reflection and Commitment. Nothing is stored server-side: the coach accepts or rejects each field and saves through the normal note endpoints. Each request is audit-logged. Without ANTHROPIC_API_KEY, the endpoint returns a clear 400; AI_NOTES_MOCK is for development only.

16Public demo

"Log In as Demo User & Take the Tour" on / and /login runs a router-aware driver.js tour across every area: an intro, Dashboard, Clients, Pipeline, Calendar, Invoices, Email Communication ×3, Library, Reports, Settings ×2 and Team. It ends by opening the client portal as a seeded client. Real users get the same tour from the Dashboard, without the portal step.

17Platform admin and observability

  • Superadmin console (/admin): workspaces with plan/suspend, users and password resets, per-workspace errors and audit log, email diagnostics with resend, registration tokens, maintenance banners (shown to every user through /api/system/banner/), feedback triage, manual platform invoices, and demo leads.
  • Errors: unhandled 500s from DRF views go to ErrorLog. Sentry is enabled when SENTRY_DSN is set. Non-DRF views (allauth, public pay/sign/session pages) only reach container logs and Sentry.
  • Health: the 30-minute site and certificate check runs from inside the host. It was added after a certbot renewal failed silently in September 2026.
  • Django admin at /django-admin/ for raw data, periodic tasks and task results.
